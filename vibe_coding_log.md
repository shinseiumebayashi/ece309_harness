## 1. Architectural Rules (Specification Driven Development)

These were fixed before any prompt was sent. The AI is not permitted to
deviate from them; a deviation is a defect, fed back for correction.

### R1. Hard constraints
- Standard C only. Permitted headers: `<stdio.h>`, `<stdlib.h>`, `<string.h>`,
  and later `<ctype.h>`.
- No external libraries.
- Must compile cleanly with `gcc -Wall -Wextra harness.c -o harness`.
- Single source file, heavily commented.

### R2. State machine
```
START
  └─> initialise empty history
      └─> LOOP
            ├─ read one line from stdin (fgets)
            ├─ if EOF (Ctrl+D)        -> goto SHUTDOWN
            ├─ if line == "exit"      -> goto SHUTDOWN
            ├─ if line starts "calc:" -> TOOL path
            └─ else                   -> MODEL path
                  └─ append (user, reply) to history, back to LOOP
SHUTDOWN
  └─> free every allocated message -> return 0
```

### R3. Memory model
- History holds at most **5 turns**. One turn = one user message + one reply.
- Storage is a **ring buffer**; on the 6th turn the oldest is freed and
  overwritten.
- Every message is heap-allocated with `malloc` and released with `free`.
  Rationale: a fixed-size array cannot leak, which would make the leak check
  meaningless. Using the heap creates a real opportunity to leak, so verifying
  that none occur actually proves something.
- Max message length: 256 characters including the terminator.

### R4. Tool execution — v1, prefix dispatch
- A line beginning with `calc:` goes to the calculator, never to the model.
- Grammar: `calc: <number> <op> <number>`, op one of `+ - * /`.
- Output: `[tool] result = <value>`

### R5. Mock model behaviour
| Input contains | Reply |
|---|---|
| `hello` or `hi` | fixed greeting |
| `history` | prints the retained turns, oldest first |
| anything else | `[model] I received: <input>` |

`history` exists so that context management is observable from a test script
without a human watching.

### R6. Robustness — the program must never crash
- Input longer than 255 chars: truncate, warn, continue.
- Division by zero: report, continue the loop.
- Unparseable `calc:` expression: report, continue the loop.
- `fgets` returning NULL: treat as `exit`, shut down cleanly.

## 2. Prompts

### Prompt 1 — initial generation (v1)

> I need a single-file C program. I am a beginner, so keep it as simple as
> possible and comment it line by line. Use only `<stdio.h>`, `<stdlib.h>` and
> `<string.h>` — no external libraries. It must compile with no warnings under
> `gcc -Wall -Wextra`.
>
> The program is a minimal "agent harness": a loop that reads user input, sends
> it either to a mock model function or to a tool function, prints the result,
> and keeps a short conversation history.
>
> Specification:
>
> 1. **Main loop.** Read one line at a time from stdin using `fgets` into a
>    buffer of 256 bytes. Strip the trailing newline.
> 2. **Exit.** If the line is exactly `exit`, or if `fgets` returns NULL,
>    break out of the loop and shut down cleanly.
> 3. **Tool dispatch.** If the line begins with `calc:`, pass the rest to a
>    function `char *run_tool(const char *expr)`. It parses
>    `<number> <op> <number>` where op is one of `+ - * /`, and prints
>    `[tool] result = <value>`. On division by zero or a parse failure, print
>    an error message and continue the loop — do not exit, do not crash.
> 4. **Mock model.** Otherwise call `char *mock_model(const char *input)`:
>    - if the input contains `hello` or `hi`, return a fixed greeting
>    - if the input is `history`, print the stored history, oldest first
>    - otherwise return `[model] I received: <input>`
> 5. **History.** Store at most 5 turns (a turn = user message + reply) in a
>    ring buffer. Each message is `malloc`'d. When a 6th turn arrives, `free`
>    the oldest before overwriting it. Free everything before returning from
>    `main`.
> 6. **Robustness.** Input longer than 255 characters is truncated with a
>    warning. The program must never crash on any input.
>
> Please write the whole thing as one `harness.c`.

**Result:** Compiled cleanly with `gcc -Wall -Wextra` on the first attempt —
no errors, no warnings, so the "paste the compiler errors back" iteration was
never needed. Manual testing then found two behavioural problems (defects 1
and 2 below), neither of which a compiler could have caught.

### Prompt 2 — test script

> I have a compiled C program named `harness` in the current directory. Write a
> Bash script `test.sh` for macOS (zsh/bash, Apple Silicon) that tests it with
> no human interaction.
>
> The program prints a `> ` prompt before each read, so expected output must be
> matched with `grep -q` rather than exact full-output comparison.
>
> Test cases:
> 1. Input `hello` → output contains `[model] Hello!`
> 2. Input `calc: 3 + 4` → output contains `[tool] result = 7`
> 3. Input `calc: 10 / 0` → output contains `division by zero`, and the program
>    still exits with status 0
> 4. Input `calc: banana` → output contains `could not parse`, and the program
>    still exits with status 0
> 5. Feed 8 turns (`a` through `h`) then `history` → output contains `d` but
>    does NOT contain `user : a`, proving the oldest turns were dropped from the
>    5-turn ring buffer
> 6. Input ends without `exit` (EOF) → program exits with status 0
>
> Print PASS or FAIL per case, count failures, and `exit 1` if any failed.
>
> **Memory check:** do NOT use valgrind — it is unavailable on Apple Silicon.
> Instead recompile with `gcc -fsanitize=address -g harness.c -o harness_debug`,
> run the same inputs through it, and FAIL if the output contains
> `LeakSanitizer` or `ERROR: AddressSanitizer`.

**Result:** All seven cases passed immediately. That turned out to be
misleading — see defect 3.

The two constraints I added by hand mattered. Without "do not use valgrind"
the script would have been built around a tool that does not exist on this
machine; without the `grep -q` instruction it would have compared full output
against expected strings and failed every case, because the harness prints a
`> ` prompt before each read.

### Prompt 3 — version 2, model-driven tool calls

> Rewrite `harness.c` so that the *model* decides when a tool runs, not the
> user. Same constraints as before: standard C only, single file, heavily
> commented, clean under `gcc -Wall -Wextra`.
>
> 1. `mock_model()` may return a sentinel line instead of an answer:
>    `TOOL_CALL: multiply(12, 5)`. Recognised tools: `add`, `subtract`,
>    `multiply`, `divide`.
> 2. `main()` detects the sentinel, calls `run_named_tool()` to execute
>    `name(a, b)`, prints the result, then calls the model a second time with
>    the tool output so it can phrase a final answer:
>    ```
>    > what is 12 * 5
>    TOOL_CALL: multiply(12, 5)
>    [tool]  result = 60
>    [model] The answer is 60.
>    ```
> 3. `mock_model()` should detect arithmetic inside ordinary prose — both
>    `12 * 5` and `12 times 5` / `100 divided by 4`.
> 4. Fix the greeting so `hi` only matches as a whole word: `this is a test`
>    must not be greeted.
> 5. Keep the `calc:` prefix working so the existing test suite still applies
>    unchanged.
> 6. If the tool refuses (division by zero, unknown tool), report it and
>    continue the loop. Still no crashes.
> 7. The two-call path allocates twice per turn — make sure the intermediate
>    strings are freed and that only the final reply enters the history.

**Result:** Compiled clean. Tests 1–6 from the v1 suite passed **unmodified**,
which is the point of having written them first: they protected the rewrite.
Three new cases (7–9) were added for the v2 behaviour. Defect 4 surfaced while
running them.

Requirement 7 was added deliberately. The v2 path allocates a sentinel string,
then a tool-output string, then a final reply, and only the last of those
belongs in the history — the obvious way to write it leaks the other two.
Naming that risk in the prompt is cheaper than finding it afterwards.

## 3. Iterations and Defects Found

| # | Symptom | Cause | Fix |
|---|---|---|---|
| 1 | `this is a test` returns the greeting | R5 was written as a substring test, so `strstr` matches the `hi` inside `this`. The AI implemented the spec correctly — the spec itself was underspecified. | v2 adds `has_word()`, which requires the characters either side of a match not to be letters. Regression-guarded by test 8. |
| 2 | `hello calc: 3 + 4` goes to the model, not the tool | R4 dispatches only on a line *prefix*, so `calc:` mid-line is invisible to the harness. | Not a bug in v1 — it is the structural limit of user-driven dispatch, and the motivation for the v2 model-driven design. |
| 3 | Test 7 reported PASS even with a deliberate leak injected | The AI built the memory check around AddressSanitizer's LeakSanitizer, which **is not implemented on macOS/Darwin**. `ASAN_OPTIONS=detect_leaks=1` was silently ignored, so the check ran but inspected nothing. | Branch on `uname`: `leaks(1)` on macOS, AddressSanitizer on Linux. Verified by re-running with the injected leak still in place — it then failed correctly and named `dup_string` as the allocation site. |
| 4 | After the v2 rewrite, tests 7–9 failed against what should have been v2 | `test.sh` only rebuilt when `./harness` was missing, so a stale v1 binary was silently tested as if it were v2. The banner in the failure output (`mini-harness.` rather than `mini-harness (v2).`) gave it away. | The script now rebuilds unconditionally on every run. |

Defect 3 is the one worth dwelling on. Every test passed, and every test was
worthless, and there was no way to tell those two states apart from the output
alone. The only thing that distinguished them was breaking the program on
purpose and watching the suite react. **A test that passes proves nothing
until you have watched it fail.**

Defects 1 and 3 point the same way: the AI did exactly what it was told, both
times. The greeting bug was a defect in my specification, not in the generated
code. The leak check was a defect in a platform assumption the AI made that I
had not thought to constrain. Reviewing generated code for whether it *matches
the spec* is not enough — the spec and its unstated assumptions have to be
reviewed too.

Defect 4 is smaller but the same shape: the failure was in the harness around
the code, not the code, and it would have been easy to misread as a bug in v2.

## 5. What SDD Actually Bought

Writing the specification first paid off in one concrete, measurable way: the
v2 rewrite changed the dispatch model, the greeting logic and the memory
lifetime of every reply, and **tests 1–6 passed unmodified afterwards**. The
suite written against v1 is what made the rewrite safe to attempt at all.

Precision in the prompt also had a visible effect. v1 compiled with no
warnings on the first attempt, which is not typical for generated C, and the
two constraints I added to the test prompt by hand — no valgrind, use `grep -q`
— were each the difference between a working script and an unusable one.

But the specification did not prevent defects 1 or 3, because both were defects
*in the specification and its assumptions*, and the AI was faithful to both.
Being precise is necessary; it is not sufficient. The AI is a fast junior
developer who never pushes back, and the failure mode that produces is not
sloppy code — it is code that satisfies exactly what you wrote and misses what
you meant. Every generated artefact, tests included, still has to be broken on
purpose before its green checkmarks mean anything.
